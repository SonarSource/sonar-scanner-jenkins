# Jenkins plugin release

Carry out an authorized release end to end. The SonarSource repository is `origin`; the Jenkins repository is `jenkins`. Maven SCM points to `jenkinsci/sonarqube-plugin`, so `release:prepare` pushes commits and the tag there. The plugin artifact is `org.jenkins-ci.plugins:sonar`.

## Establish the release state

1. Read the current `pom.xml` revision and changelist, latest `sonar-*` tag, branch, `git status`, remotes, and any `release.properties` or `pom.xml.releaseBackup`. Preserve pre-existing work. An old release descriptor is not evidence that the current release has run.
2. Fetch or query **live** `origin/master`, `jenkins/master`, and the intended release tag. Stop if the version or remote history is ambiguous. Add the `jenkins` remote if absent: `git@github.com:jenkinsci/sonarqube-plugin.git` (HTTPS is also valid). Do not overwrite an existing remote without checking it.
3. Verify that the authenticated operator can push to the Jenkins repository and has a Jenkins Maven deployment credential. Check that Maven can parse user and global settings, and that the server ID required by the Jenkins plugin parent POM is present (usually `maven.jenkins-ci.org`); parse the Maven XML namespace correctly. Verify the credential with a read-only authenticated Jenkins repository request before `release:prepare`; a configured server entry alone does not prove it works. Never print passwords, tokens, complete settings, or credential-bearing URLs. If missing or rejected, tell the user to obtain the settings from `https://repo.jenkins-ci.org/setup/settings.xml` with their Jenkins account and install the server entry locally. If they lack maintainer permissions, direct them to the Jenkins plugin hosting/maintainer request process before continuing.
4. Use the SonarSource Atlassian Jira site (`sonarsource.atlassian.net`) for the `REL` issue; do not use Jenkins Jira. Search for an existing ticket for the exact release version before creating one. The REL issue type is `Ask for release`. Discover current required fields from Jira metadata; as of November 2026 these include `customfield_10145` (Jira release notes URL), `customfield_10146` (short description), and `customfield_10147` (documentation status). Assign the ticket to the authenticated release operator. If Jira automation is unavailable, give the user a ready-to-enter title and description and request the issue key. Verify the latest quality gate is green, record its status, and stop before any release mutations if it is red. If access to the quality gate is missing, ask for specific evidence; do not claim it passed.

## Release

5. Commit or otherwise account for all intended source changes and ensure the working tree is safe for Maven release. When it contains pre-existing release files or skill edits, use a separate clean clone on `master` with the real `origin` and `jenkins` remotes; preserve the user's files. Bring the release clone up to date with live `origin/master` using a fast-forward, push that exact commit to `jenkins/master`, then verify both live master refs have the same hash. Investigate divergence instead of force pushing.
6. Run `mvn -B release:prepare release:perform -Darguments="-DskipITs -DskipTests" -DdryRun` as a single command first. Inspect the proposed version, tag, commits, and result. Then run `mvn -B release:clean` in the clean release clone. Verify that no tracked changes or Maven release files (`release.properties`, `pom.xml.releaseBackup`, `pom.xml.tag`, `pom.xml.next`) remain before the real run; otherwise investigate instead of resuming the dry run.
7. If Git is configured to sign tags, confirm the configured GPG key can sign without an interactive prompt in this process. Have the operator unlock it in their own terminal if needed; never request the passphrase. Run `mvn -B release:prepare release:perform -Darguments="-DskipITs -DskipTests"` as a single command. Run it once. If it fails, inspect the release phase, live Jenkins tag, deployment repository, and local release state before any retry; never blindly rerun a step that may have published artifacts.
8. Verify the public HPI for the intended version and Maven metadata at `https://repo.jenkins-ci.org/public/org/jenkins-ci/plugins/sonar/`, and verify the signed Jenkins tag. Push the signed tag to `origin`. Keep SonarSource `master` protection and rulesets enabled. Push a release sync branch and open a PR for the release commits; changing protection requires separate, explicit authorization from repository administrators. This repository's `PullRequestCreated` workflow treats a Jira key in the PR body as a parent ticket. Keep the REL key out of the PR body because that workflow is configured for `SONARJNKNS` subtasks. Check the PR automation and CI, and report the required review and merge as outstanding.
9. Compare the live release tag in both repositories. Reassign the `REL` issue to the PM (Chris) after publication; use the actual Jira account identity, not a guessed username. Report links, hashes, artifact coordinates, and any unfinished steps.

If Maven reports a PKIX trust-chain failure, first diagnose the certificate or proxy. As an exceptional workaround for the Jenkins repository only, the documented flags are `-Dmaven.wagon.http.ssl.insecure=true -Dmaven.wagon.http.ssl.allowall=true -Dmaven.wagon.http.ssl.ignore.validity.dates=true -Dmaven.resolver.transport=wagon`. Put them inside `-Darguments` for the forked `release:perform` Maven process; passing them only to the outer command will not fix deployment. Disclose their use. If deployment returns 401, verify the Jenkins credential and upload permission without displaying secrets. If deployment fails after prepare, verify which artifacts exist before retrying only `release:perform`. If a SNAPSHOT appears in the release repository, follow the Jenkins plugin hosting release troubleshooting guide before taking further release actions.

If GPG tag signing fails because pinentry needs an interactive terminal, inspect `release.properties` and the live Jenkins commit, tag, and artifact before recovery. Have the operator unlock their configured signing key in their own terminal without sharing its passphrase. Resume the same Maven prepare/perform release from the recorded phase with `-Dresume=true`; do not disable tag signing or start a new release. Verify the signed tag after recovery.
